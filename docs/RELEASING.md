# Releasing

1. `npm run lint && npm run typecheck && npm test && npm run test:render && npm run build:app && npm run test:e2e` (the link tests run the built server, as the desktop app does)
2. The version goes up by itself. Every push to main that changes the app gets the next version from the `version` workflow (`.github/workflows/version.yml`, `scripts/version-bump.mjs`): within a minute of the push it commits `0.1.5` after `0.1.4`, in the root and `apps/studio/package.json`, the lockfile and the changelog (`apps/site/content/changelog.json`), and the pipeline publishes it from that commit. A push that changes only the docs, the site, tests, CI or the release scripts gets no version. Pull before the next push: main has that commit, and the next push is refused until the checkout has it too.

   The changelog entry lists the commits that changed the app. To write it yourself, put it under `"next"` in the changelog, `{ "title": "...", "items": ["..."] }`, in or before the push: the next version takes it. To skip to a bigger number, add `"version": "0.2.0"` there. Setting the version in a push yourself works too, with its changelog entry: the workflow leaves that push alone.
3. Publish it, in one of two ways. Either way the files go up with a `SHA256SUMS.txt` to `v<version>` in the FileFreak release folder, the folder is checked for each system's file and its SHA-256 the way installed apps read it, and installed apps are offered the version from then on.

   **Push it.** A push to main starts the pipeline in EZPIPELINE (`knitted release`). When the release folder has no finished `v<version>`, the pipeline builds the installers on its Linux host (`scripts/pipeline-release.mjs`): macOS (Apple silicon and Intel) as a `.zip`, Windows (x64) and Linux (x64 and ARM). Not the macOS `.dmg`, which only macOS can make. electron-builder signs Mac apps only on a Mac, so the pipeline signs them itself with rcodesign, ad-hoc like a Mac build (`scripts/mac-sign.mjs`). It uploads them, then builds the site, so the Download page shows the new version. Installed Macs update from the `.zip`, as from any release. Mac visitors get the `.zip`, with the newest `.dmg` there is (an earlier version's) offered beside it, and that updates itself once installed. Any other run publishes nothing. The pipeline needs `FILEFREAK_KEY`, the release folder's write key (`ci/ezpipeline/knitted-release.env.example`). To try the build on Linux without uploading: `NODE_ENV=production node scripts/pipeline-release.mjs --no-upload`.

   **On a Mac, `npm run release`.** Run it once the pipeline has published the version, after pulling its commit. It builds every installer, the `.dmg` too, uploads them, and checks them. It refuses a checkout that changes the app since the version was set, since apps on that version would never be offered those changes: push them, and they get a version of their own. Last, it pushes this checkout to main, which starts the pipeline, and waits until the Download page lists these files, a few minutes. The version is up by then, so the pipeline only builds the site. If the checkout has nothing to push, nothing starts that build, and it says to run the pipeline in EZPIPELINE. Running a version again replaces its files: run on a version the pipeline published, it puts the Mac's files in place of the pipeline's and adds the `.dmg`. The page shows them once the site is built again.

   It needs one key in `.env` (see `.env.example`): `FILEFREAK_KEY`, the release folder's write key. Before it builds anything it checks that the key can write, and that this checkout has everything on `origin/main`, since the installers are built from here.
4. On a clean machine per system, install from the uploaded files, go offline, and run the first journey: make a project, upload a photo, build a pattern, knit a PNG and an MP4. Note the time.

The site is static: its Download page and `/releases.json` list the release folder as it was when the site was built. A visitor's browser cannot read the folder itself. FileFreak refuses a key sent from a web page, and its public answers (`/api/public/files/...`, which need no key) send no `Access-Control-Allow-Origin`, so a page on another site may not read them. If they did, as FileFreak's `/v1` API does, the Download page could read the folder live, as the apps do.

Each installer carries its own system's ffmpeg, ffprobe and sharp, fetched once into `node_modules/.cache` by `scripts/desktop-binaries.mjs` and checked to be built for that system. This machine's copies, the ones npm installed, fit no other system.

Local build without uploading: `npm run desktop:dist` builds the installers for this machine's system, in `dist/desktop`. For a quick check without an installer, `npm run desktop:pack` and open the app in `dist/desktop/<platform>`.

On Linux, two things go differently, both in the pipeline's build. The Mac app is signed in `scripts/after-pack.mjs`, since electron-builder signs only on a Mac. And electron-builder makes the Windows uninstaller by running the new installer under Wine, except on a Mac, where it reads the uninstaller out of the installer instead. Wine has no ARM Linux build, so `pipeline-release.mjs` takes the Mac's way there too.

The `release` GitHub workflow (tag `v*`) builds the same installers on GitHub's runners, one per system, into a draft GitHub release. It does not upload to FileFreak.

## Updates

Installed apps read the release folder itself, through FileFreak's public answers (no key: the folder is public), so a release reaches them as soon as step 3 has uploaded it. An up-to-date copy asks for one listing; one with an update also reads that version's folder and its `SHA256SUMS.txt`. That file goes up after every installer, so a version without it is still uploading and is not offered yet. If the folder cannot be read, they ask the site's `/releases.json` (`apps/site/app/releases.json`, the list the Download page shows, built from the same folder). Copies before 0.1.2 only ask the site, so they see a release once the site has been built after it, which the end of step 3 waits for. The updater (`apps/studio/electron/update.mjs`) installs the Mac `.zip`, the Windows `.exe` and the Linux `.AppImage`, so a release needs those, and only installs a file whose SHA-256 its `SHA256SUMS.txt` records. Versions must go up. A test version such as `0.2.0-beta.1` is offered only to copies that are test versions themselves.

To check the swap by hand on a Mac, pack two versions into a scratch folder: `npx electron-builder --dir --mac --arm64 -c.directories.output=<old>`, then `npx electron-builder --mac zip --arm64 -c.extraMetadata.version=<next> -c.directories.output=<new>` (in `apps/studio`). Serve a `releases.json` on 127.0.0.1 that lists the zip and its SHA-256, and open the old app with `KNITTED_UPDATE_URL=http://127.0.0.1:<port>/releases.json` and `--user-data-dir=<scratch>`, so it does not touch your own settings or library.

## Signing (when certificates exist)

Today the Mac app is ad-hoc signed (`identity: "-"` in `apps/studio/electron-builder.yml`): its signature is whole, so macOS does not call it damaged, but it names no developer, so a downloaded copy opens only after **Open Anyway** (docs/INSTALL.md). An Apple Developer ID and notarisation remove that step.

macOS: delete `identity: "-"` and `hardenedRuntime: false` from `mac` (notarisation needs the hardened runtime, which is the default, and electron-builder's default entitlements allow what Electron needs), and add the Developer ID Application certificate to `.env` as `CSC_LINK` and `CSC_KEY_PASSWORD`. Notarisation runs when `APPLE_API_KEY`, `APPLE_API_KEY_ID` and `APPLE_API_ISSUER` are set, or `APPLE_ID`, `APPLE_APP_SPECIFIC_PASSWORD` and `APPLE_TEAM_ID`. `npm run release` passes `.env` to electron-builder. Windows: `CSC_LINK`/`CSC_KEY_PASSWORD` for the NSIS target. Nothing else changes for a Mac's release. The pipeline signs its Mac app with rcodesign (`scripts/mac-sign.mjs`), which signs with a certificate given as a `.p12` (`--p12-file`, `--code-signature-flags runtime` for the hardened runtime) and notarises with an App Store Connect API key (`rcodesign notary-submit --staple`): that is where the same change goes there.

## Downgrading

Install the older release over the newer one. The library format is migrated forward only, so keep a backup (Settings, Storage) before updating across a version that changes it.
